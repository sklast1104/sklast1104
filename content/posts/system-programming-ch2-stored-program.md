> 시스템 프로그래밍 강의 내용을 정리한 노트임.

## 1. 스토어드 프로그램 (Stored Program)

스마트폰에서 게임을 하다가 메신저를 켤 수 있는 이유가 뭘까? 하드웨어를 교체하지 않고도 소프트웨어만 바꿔서 다른 일을 할 수 있는 이유. 이게 **스토어드 프로그램** 컨셉 덕분이다.

### 과거: 하드와이어드 방식

과거의 컴퓨터는 특정 계산을 수행하려면 전선을 일일이 다시 연결해야 했다. 다른 계산을 하려면 물리적으로 배선을 변경해야 하는 방식.

### 폰 노이만의 아이디어

**폰 노이만(Von Neumann)**이 제안한 핵심 아이디어:

> **"프로그램(명령어의 집합) 자체를 데이터처럼 메모리에 저장하자"**

이 설계 원칙 덕분에 하드웨어를 교체하지 않고 소프트웨어만 바꿔서 다른 작업을 수행할 수 있게 됨.

```
[하드와이어드 방식]                    [스토어드 프로그램 방식]

  계산 A를 하려면                       메모리에 프로그램 A 로드 → 실행
  → 전선 연결 변경                      메모리에 프로그램 B 로드 → 실행
                                        메모리에 프로그램 C 로드 → 실행
  계산 B를 하려면
  → 전선 또 변경                        하드웨어 변경 없이 소프트웨어만 교체
```

## 2. 소스 코드에서 실행 파일까지

CPU는 이진수(Binary Code)만 이해한다. 그런데 사람이 0과 1로 프로그래밍하기는 사실상 불가능하므로, **어셈블리어(Assembly)** 라는 문자 형태의 별칭(ADD, SUB 등)을 만들어 사용했다. 이걸 다시 바이너리로 변환하는 게 **어셈블러(Assembler)**.

오늘날 소스 코드가 실행 파일이 되기까지의 과정:

```
  소스 코드 (.c / .cpp)
       │
       ▼
  ┌──────────────────┐
  │  1. 전처리기       │  #include, #define 등 지시자 처리
  │  (Preprocessor)   │  → 소스 코드 확장
  └────────┬─────────┘
           ▼
  ┌──────────────────┐
  │  2. 컴파일러       │  고수준 언어 → 어셈블리어로 번역
  │  (Compiler)       │  (ADD, MOV 등 CPU 명령어 별칭)
  └────────┬─────────┘
           ▼
  ┌──────────────────┐
  │  3. 어셈블러       │  어셈블리어 → 바이너리 코드로 변환
  │  (Assembler)      │  (CPU가 실제로 인식하는 0과 1)
  └────────┬─────────┘
           ▼
  ┌──────────────────┐
  │  4. 링커          │  바이너리 코드 + 라이브러리를
  │  (Linker)         │  하나로 묶어 실행 파일 완성
  └────────┬─────────┘
           ▼
     실행 파일 (.exe)
           │
           ▼
     메모리(RAM)에 로드 → CPU 실행
```

중요한 점: **명령어 디자인(ISA)**과 CPU 하드웨어 디자인은 서로 긴밀하게 연결되어 있다. CPU는 특정 이진수 명령어(예: `001` = 덧셈)를 처리하기 위해 그에 맞는 회로 구조가 결정됨. ISA가 먼저 설계되고, 그걸 처리할 수 있는 CPU가 만들어지는 구조다.

## 3. Fetch - Decode - Execute 사이클

1장에서 다뤘던 내용의 재정리. CPU가 명령어를 처리하는 3단계:

| 단계 | 명칭 | 담당 | 역할 |
|------|------|------|------|
| 1 | **Fetch** (패치) | Bus Interface | 메모리의 명령어를 CPU 내부로 가져옴 |
| 2 | **Decode** (디코드) | Control Unit | 가져온 명령어가 무엇인지 해석 |
| 3 | **Execute** (실행) | ALU + 기타 | 연산 수행 및 결과 도출 |

Execute 단계는 ALU 혼자 하는 일이 아니다. 메모리에서 필요한 데이터를 추가로 가져오거나, 결과를 다시 메모리에 쓰는 등 **여러 구성 요소가 협력하는 넓은 의미의 실행 과정**임.

## 4. 시스템 버스 (System Bus)

CPU와 메모리 사이에 정보를 교환하기 위한 전용 통로. 목적에 따라 3종류로 나뉜다.

```
                    ┌─────────────┐
                    │     CPU     │
                    └──────┬──────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
   ┌──────┴──────┐  ┌─────┴──────┐  ┌──────┴──────┐
   │ Address Bus │  │  Data Bus  │  │ Control Bus │
   │  (주소)      │  │  (데이터)   │  │  (제어)      │
   │             │  │            │  │             │
   │  단방향 ↓    │  │  양방향 ↕   │  │  양방향 ↕    │
   └──────┬──────┘  └─────┬──────┘  └──────┬──────┘
          │                │                │
          └────────────────┼────────────────┘
                           │
                    ┌──────┴──────┐
                    │   메모리     │
                    └─────────────┘
```

### Address Bus (주소 버스)

데이터가 위치한 메모리 주소를 지정하는 통로. CPU가 메모리에 "몇 번지 데이터를 달라"고 요청하는 용도이므로 **단방향**(CPU → 메모리).

### Data Bus (데이터 버스)

실제 명령어와 데이터를 실어 나르는 핵심 통로. CPU가 읽기도 하고 쓰기도 해야 하므로 **양방향**.

### Control Bus (제어 버스)

Data Bus가 양방향이기 때문에 생기는 문제를 해결하는 교통 정리 역할. 누군가 동시에 데이터를 보내면 충돌이 발생한다. Control Bus가 "지금은 읽기 차례", "지금은 쓰기 차례"라는 신호를 보내서 **통신 순서를 조율**함.

## 5. 전체 흐름 정리

스토어드 프로그램 컨셉 위에서 모든 하드웨어가 유기적으로 동작하는 전체 흐름:

```
┌─────────────┐         시스템 버스            ┌──────────────────────┐
│             │  ◀── Address Bus ──────────▶  │                      │
│  메모리(RAM) │  ◀── Data Bus ────────────▶  │        CPU           │
│             │  ◀── Control Bus ─────────▶  │                      │
│  ┌────────┐ │                               │  ┌───────────────┐  │
│  │명령어 1 │ │  ──── Fetch ────────────────▶ │  │  Register     │  │
│  │명령어 2 │ │                               │  └───────┬───────┘  │
│  │명령어 3 │ │                               │          │          │
│  │ ...    │ │                               │          ▼          │
│  │데이터   │ │                               │  ┌───────────────┐  │
│  └────────┘ │                               │  │ Control Unit  │  │
│             │                               │  │  (Decode)     │  │
│             │                               │  └───────┬───────┘  │
│             │                               │          │ 신호     │
│             │                               │          ▼          │
│             │                               │  ┌───────────────┐  │
│             │  ◀── 결과 저장 ───────────────  │  │     ALU       │  │
│             │                               │  │  (Execute)    │  │
└─────────────┘                               │  └───────────────┘  │
                                              └──────────────────────┘
```

1. 실행 파일이 **메모리(RAM)**에 로드됨
2. CPU가 **Address Bus**로 주소를 지정하고, **Data Bus**로 명령어를 가져옴 (Fetch)
3. **Control Unit**이 명령어를 해석 (Decode)
4. **ALU**가 다른 장치들과 협력하여 연산 수행 (Execute)
5. 결과를 다시 메모리에 저장하거나 다음 명령어로 진행

이 사이클이 반복되면서 프로그램이 실행됨. 하드웨어를 교체하지 않고 메모리에 다른 프로그램을 로드하면 다른 작업을 수행할 수 있다는 것이 스토어드 프로그램의 핵심.

### 핵심 요약

| 개념 | 내용 |
|------|------|
| **스토어드 프로그램** | 프로그램을 데이터처럼 메모리에 저장하여 소프트웨어 교체만으로 다른 작업 수행 |
| **빌드 과정** | 전처리기 → 컴파일러 → 어셈블러 → 링커 → 실행 파일 |
| **ISA** | 명령어 설계. CPU 하드웨어 구조를 결정하는 근간 |
| **Address Bus** | 메모리 주소 지정 (단방향) |
| **Data Bus** | 실제 데이터 전송 (양방향) |
| **Control Bus** | 통신 순서 조율, 충돌 방지 (양방향) |
