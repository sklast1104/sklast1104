> 시스템 프로그래밍 강의 내용을 정리한 노트임.

## 1. 문자 셋 (Character Set)

컴퓨터가 문자를 식별하고 표시하기 위해 사용하는 **문자들의 집합**. 각 문자에 고유한 숫자 값을 매핑한 규칙이다. 한 문자를 표현하는 바이트 수에 따라 3가지로 분류됨.

### SBCS (Single Byte Character Set)

모든 문자를 **1바이트(8비트)**로 표현. 대표적으로 **ASCII**.

```
문자:   A    B    C    !    ?
바이트: [41] [42] [43] [21] [3F]
         1B   1B   1B   1B   1B
```

- 표현 가능 문자: 최대 256개
- 영문권에서는 충분하지만 한글, 일본어 등 다국어 표현 불가

### MBCS (Multi Byte Character Set)

문자 종류에 따라 바이트 수가 **가변적**. 영문은 1바이트, 한글은 2바이트.

```
문자:   A    B    C    한      글
바이트: [41] [42] [43] [C7 D1] [B1 DB]
         1B   1B   1B    2B      2B
```

- ASCII 호환성 유지하면서 다국어 표현 가능
- 단, 문자열 처리 시 심각한 문제 발생 (후술)

### WBCS (Wide Byte Character Set)

모든 문자를 **고정 2바이트(16비트)**로 표현. 대표적으로 **유니코드(Unicode)**.

```
문자:   A       B       C       한       글
바이트: [00 41] [00 42] [00 43] [D5 5C] [AE 00]
          2B      2B      2B      2B      2B
```

- 모든 언어를 동일한 크기로 처리
- 메모리는 더 쓰지만 로직이 단순하고 안정적
- **현대 Windows API의 표준**

---

## 2. SBCS vs MBCS vs WBCS 비교

| 방식 | 대표 | 영문 | 한글 | 특징 |
|------|------|------|------|------|
| SBCS | ASCII | 1B | 불가 | 단순하지만 서구권 전용 |
| MBCS | ANSI (KSC5601 등) | 1B | 2B | 메모리 효율적이나 처리 복잡 |
| WBCS | Unicode | 2B | 2B | 메모리 더 쓰지만 안정적, Windows 표준 |

---

## 3. MBCS의 한계: 왜 유니코드가 필수인가

MBCS는 겉보기에 효율적이지만, **문자 수와 바이트 수가 불일치**하는 문제가 있다. 실제 개발에서 치명적인 버그를 만듦.

### 예시: `"ABC한글"` 문자열

```
메모리 레이아웃:

[A ][B ][C ][한   ][글   ][\0]
 41  42  43  C7 D1  B1 DB  00
 1B  1B  1B   2B     2B    1B   = 총 8바이트
```

- `sizeof` 결과: **8** (널 문자 포함 전체 바이트)
- `strlen` 결과: **7** (널 문자 제외 바이트 수)
- 실제 문자 수: **5개** (A, B, C, 한, 글)

### 문제: 반복문 실행 오류

프로그래머가 "5개 문자니까 5번 반복"으로 루프를 작성하면:

```
반복 1: [41]       → 'A'     (정상)
반복 2: [42]       → 'B'     (정상)
반복 3: [43]       → 'C'     (정상)
반복 4: [C7]       → ???     (한글의 앞바이트만 읽음 → 깨짐)
반복 5: [D1]       → ???     (한글의 뒷바이트 → 깨짐)
```

`strlen`이 반환한 7을 기준으로 처리해도 바이트 단위 접근이 되어 데이터가 깨진다. 문자와 바이트가 1:1 대응이 안 되기 때문에 발생하는 근본적인 문제.

### 유니코드가 필수인 이유

현대 환경은 모바일 기기조차 충분한 메모리를 가지고 있다. MBCS의 가변 바이트로 인한 **로직 버그 처리 비용**이 유니코드 사용 시 늘어나는 메모리 비용보다 훨씬 크다. 유니코드에서는 모든 문자가 2바이트이므로 문자 수 = 바이트 수 / 2로 항상 일관됨.

## 4. 유니코드 프로그래밍 실전

C/C++에서 유니코드 프로그램을 만들려면 **자료형, 리터럴, 함수** 3가지를 바꿔야 한다.

### 자료형: `char` → `wchar_t`

```c
// MBCS
char str[] = "Hello";        // 1바이트 문자

// WBCS (유니코드)
wchar_t str[] = L"Hello";    // 2바이트 문자
```

`wchar_t`는 ANSI 표준으로 등록된 기본 자료형. 별도 구조체가 아님.

### 리터럴: `L` 접두사

```c
// 아스키 리터럴
"ABC"      // 각 문자 1바이트로 저장

// 유니코드 리터럴
L"ABC"     // 각 문자 2바이트로 저장
```

`L` 접두사는 컴파일러에게 "이 데이터를 2바이트 유니코드로 할당하라"고 지시하는 것.

### 함수 전환

기존 ASCII 함수는 유니코드 문자열과 포인터 타입이 맞지 않아 컴파일 에러가 발생함. 유니코드 전용 함수로 교체해야 한다:

| SBCS/MBCS | WBCS (유니코드) | 기능 |
|-----------|----------------|------|
| `strlen` | `wcslen` | 문자열 길이 |
| `strcpy` | `wcscpy` | 문자열 복사 |
| `printf` | `wprintf` | 문자열 출력 |
| `scanf` | `wscanf` | 문자열 입력 |

## 5. 엔트리 포인트의 유니코드화: `wmain`

프로그램 내부를 유니코드로 전환해도, 엔트리 포인트에서 OS가 넘겨주는 인자가 ASCII면 의미가 없다. 마지막 퍼즐은 **`wmain`**.

```c
// 기존 (ASCII)
int main(int argc, char* argv[])

// 유니코드
int wmain(int argc, wchar_t* argv[])
```

`wmain`을 사용하면 OS가 명령 프롬프트를 통해 전달하는 인자들을 `wchar_t*` 타입으로 구성해서 전달한다. 프로그램 내부뿐 아니라 **시스템과의 인터페이스에서도** 인코딩 오류 없이 일관된 유니코드 환경을 유지할 수 있음.

```
┌──────────────┐     wchar_t*     ┌──────────────────┐
│  OS / Shell  │ ───────────────▶ │  wmain(argc,     │
│  (인자 전달)  │                  │        argv)     │
└──────────────┘                  └────────┬─────────┘
                                           │
                                           ▼
                                  ┌──────────────────┐
                                  │  wchar_t 자료형    │
                                  │  L"..." 리터럴     │
                                  │  wcs* 함수         │
                                  │                    │
                                  │  유니코드 파이프라인 │
                                  │  완성              │
                                  └──────────────────┘
```
